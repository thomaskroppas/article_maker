# CLAUDE.md — SEO Pipeline (веб-версия)

Ты разрабатываешь веб-приложение для автоматической генерации SEO-статей **с нуля** по техническому заданию. Существует рабочая desktop-версия (PySide6) — она лежит в `reference_impl/` как референс поведения.

## Источники истины (по убыванию приоритета)

1. **`docs/TZ_v1.2.md`** — техническое задание. Единственный источник требований. Все решения заказчика уже внесены в текст.
2. **`PLAN.md`** — порядок работ. Задачи выполняются строго последовательно, по одной.
3. **`docs/ARCHITECTURE.md`** — описание desktop-версии. Только для понимания логики; при расхождении с ТЗ — ТЗ главнее.
4. **`reference_impl/`** — код desktop-версии. Сверяться с логикой можно и нужно; **копировать код нельзя** (там Qt-архитектура, глобальное состояние и известные баги, перечисленные в ARCHITECTURE.md, раздел 15).

## Жёсткие правила (нарушать нельзя)

- **Промпты `prompts/<agent>/v1.txt` использовать как есть.** Не редактировать, не «улучшать», не переформатировать. Это ключевая ценность системы, откалиброванная на реальных прогонах. Исключение: два новых промпта (sources_weaver, fact_checker) ты пишешь сам — критерии в ТЗ п. 20.5.
- **Схемы данных (ТЗ раздел 13), веса QA (п. 6.15) и константы (п. 6.2.1) не менять.** Если в ходе работы кажется, что схему надо изменить — остановись и задай вопрос заказчику, не реализуй «как проще».
- **Раздел 23 ТЗ (Out of scope) обязателен** — перечисленное там не реализуется, даже если «легко добавить».
- **Секреты не коммитить.** `env_with_keys.txt` и `.env` в `.gitignore`. В коде и логах ключи не печатать.
- **Живые LLM-вызовы — только в задачах, где это явно указано в PLAN.md** (T-14 и приёмка). Во всех остальных задачах используется MockLLMClient + fixtures. Каждый живой прогон статьи стоит $0.05–0.15 реальных денег заказчика.

## Стек (зафиксирован в ТЗ, раздел 4)

Backend: Python 3.11+, FastAPI, Celery + Redis, PostgreSQL 15 (образ `pgvector/pgvector:pg15`), SQLAlchemy 2.0 + Alembic, Pydantic v2, anthropic SDK, BeautifulSoup4 + readability-lxml, pysbd, Pillow.
Frontend: React + Vite, тёмная тема (Catppuccin-inspired), WebSocket-клиент.
Инфраструктура: Docker Compose (сервисы: postgres, redis, backend, worker, frontend; nginx — только profile `production`).

## Структура репозитория

```
backend/          # FastAPI + Celery worker (создаётся в T-1)
frontend/         # React SPA (создаётся в T-1)
prompts/          # промпты агентов — источник, монтируется в контейнеры
fixtures/         # реальные примеры форматов — основа тестов
reference_article/ # полный прогон эталонной статьи (Байкал, QA 89)
seed/             # справочники ниш и архетипов → в Alembic-миграцию (T-3)
docs/             # ТЗ и архитектура
reference_impl/   # desktop-версия, только чтение
```

## Рабочий цикл

1. Открой `PLAN.md`, возьми первую незакрытую задачу.
2. Прочитай указанные в задаче разделы ТЗ **перед** написанием кода.
3. Сначала тесты (на fixtures, где применимо), потом реализация.
4. Definition of Done задачи выполнен → `pytest` зелёный → один коммит с префиксом задачи (`T-03: ...`) → отметь задачу в PLAN.md → следующая.
5. Вопросы к заказчику собирай в `QUESTIONS.md` (создай при первом вопросе). Блокирующий вопрос — остановись и сообщи; неблокирующий — зафиксируй допущение в QUESTIONS.md и продолжай.

## Команды

```bash
docker compose up -d                        # окружение (без nginx)
docker compose exec backend pytest -x -q    # тесты backend
docker compose exec backend alembic upgrade head
cd frontend && npm run dev                  # фронт в dev-режиме
```

До T-1 команды недоступны — их создаёшь ты.

## Проверка окружения (входит в T-0)

Шаг 1 (SERP) работает через интерфейс `SerpProvider`; основной провайдер — **serper.dev**. Тестовый запрос (один раз, списывает 1 кредит бесплатного аккаунта):

```bash
curl -m 10 -X POST "https://google.serper.dev/search" \
  -H "X-API-KEY: $SERPER_API_KEY" -H "Content-Type: application/json" \
  -d '{"q":"test","gl":"ru","hl":"ru"}'
```

Альтернативный провайдер (xmlstock) проверяется только если задан `XMLSTOCK_API_URL`:

```bash
curl -m 10 "$XMLSTOCK_API_URL?q=test&geo=ru&hl=ru"
```

Если основной провайдер недоступен — это блокер, сообщи заказчику немедленно (можно переключиться на альтернативу через настройку `serp_provider`). Разработка шагов 2+ возможна на `fixtures/serp_bundle_example.json`, но приёмка без живого провайдера не пройдёт. **Живые вызовы serper.dev в тестах запрещены** (каждый запрос — кредит): только моки и кэш.

## Тестовая дисциплина

- Pydantic-схемы валидируются против **реальных** файлов из `fixtures/` и `reference_article/` — если схема не принимает реальный файл, ошибка в схеме, а не в файле.
- MockLLMClient возвращает содержимое fixtures по имени агента — пайплайн до T-14 гоняется полностью офлайн.
- SERP в разработке — только из кэша (`serp_json_path` на fixture); живой SERP-провайдер (serper.dev / xmlstock) в тестах не дёргать — все три провайдера тестируются на моках.
- Coverage критических модулей (агенты, QA-метрики, кэши) ≥ 60% — критерий приёмки 21.3.
